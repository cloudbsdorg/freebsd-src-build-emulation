# Emulation Framework — Agent Workflow Instructions

> **Purpose:** This document defines how autonomous agents (and human developers) should consume the plan documents, pick tasks, claim work, commit changes, and handle merge conflicts when multiple agents work on the same branch concurrently.
>
> **Note for agents:** Read this document **before** starting any task. Follow these instructions exactly. If any step is unclear, ask for clarification.

---

## 0.1.1 Overview

This project uses a **shared branch model** where multiple agents may be working on the same Git branch simultaneously. To avoid conflicts and ensure traceability, every task must be claimed, tracked, and completed following a strict protocol.

**Key principles:**
- **Claim before work** — Never start a task without first claiming it in the document
- **Check dependencies** — Never start a task whose dependencies are not yet complete
- **Commit frequently** — Commit after each task completion, not after every file edit
- **Handle conflicts gracefully** — If a merge conflict occurs, determine if the task was taken by another agent

## 0.1.2 Task Selection

### 0.1.2.1 How to Pick a Task

1. **Consult the TOC** — Open [`0.0-Emulation-TOC.md`](./0.0-Emulation-TOC.md) to understand the document structure
2. **Read the relevant document** — Open the document containing the task you want to work on
3. **Find an unclaimed task** — Look in the task tables for a row where:
   - `Status` is empty or `⬜ PENDING`
   - `Assigned To` is empty
   - `Start` is empty
4. **Check dependencies** — Verify that all tasks listed in the `Dependencies` column are marked as `✅ DONE` or have a completed `End` date
5. **If dependencies are not met** — Do NOT start the task. Either:
   - Pick a different task whose dependencies are met, OR
   - Work on completing the blocking dependency first

### 0.1.2.2 Priority Order

Tasks should generally be worked on in the following order:

1. **Phase S0 tasks** (kernel module security infrastructure) — highest priority, blocks everything
2. **Phase 1 tasks** (build system integration) — blocks all kernel code
3. **Phase 2 tasks** (kernel-side framework) — blocks architecture and userland
4. **Phase S1-S6 tasks** (security implementation) — blocks production use
5. **Phase 3-6 tasks** (architecture, devices, userland) — feature implementation
6. **Phase 7-9 tasks** (debugging, testing, documentation) — quality assurance

Within each phase, tasks with the most dependencies should be started first.

## 0.1.3 Claiming a Task

### 0.1.3.1 Before You Start

Before claiming a task, ensure:

- [ ] You have read this workflow document
- [ ] You have read the relevant plan document(s)
- [ ] You understand the task requirements
- [ ] All dependencies are marked as complete
- [ ] No other agent has claimed the task (check `Assigned To` column)

### 0.1.3.2 How to Claim

To claim a task, update the task table row in the document:

1. **Set `Status`** to `🔄 IN PROGRESS`
2. **Set `Assigned To`** to your agent identifier using the system hostname (e.g., `freedev002`). Use the `hostname` command to identify your system.
3. **Set `Start`** to the current date/time in ISO 8601 format: `YYYY-MM-DD HH:MM UTC`
4. **Leave `End` empty** — will be filled on completion

**Example — Before claiming:**

| ID | Task | Status | Assigned To | Owner | Start | End | Dependencies | Files | Notes |
|----|------|--------|-------------|-------|-------|-----|--------------|-------|-------|
| S0.1 | Create `emu_mod.c` with MODULE_DEPEND | ⬜ PENDING | | | | | | `sys/emulation/emu_mod.c` | |

**Example — After claiming:**

| ID | Task | Status | Assigned To | Owner | Start | End | Dependencies | Files | Notes |
|----|------|--------|-------------|-------|-------|-----|--------------|-------|-------|
| S0.1 | Create `emu_mod.c` with MODULE_DEPEND | 🔄 IN PROGRESS | freedev002 | | 2026-04-26 04:37 UTC | | | `sys/emulation/emu_mod.c` | |

### 0.1.3.3 Commit and Push After Claiming

After claiming a task, immediately commit and push the change:

```bash
git add .plan/<document>.md
git commit -m "Claim task <ID>: <brief description>" --trailer "Co-authored-by: Junie <junie@jetbrains.com>"
git push
```

**Important:** You must push immediately after committing. Other agents working on the same branch need to see your claim to avoid starting the same task. The claim is not effective until it is pushed to the remote repository.

## 0.1.4 Working on a Task

### 0.1.4.1 Implementation Guidelines

1. **Follow the plan** — Implement exactly what the task describes. Do not add scope.
2. **Follow code style** — Match the existing codebase conventions (see `CONTRIBUTING.md` if present)
3. **Write tests** — Every task that involves code changes must include tests
4. **Update cross-references** — If you change a section number or file name, update all cross-references
5. **Document as you go** — Update KDoc/comments in code, not just plan documents

### 0.1.4.2 If You Get Stuck

If you encounter an issue that blocks progress:

1. **Try 3 genuine fix attempts** — Document what you tried and why it didn't work
2. **Mark the task as blocked** — Set `Status` to `🟡 BLOCKED` and add the reason to `Notes`
3. **Commit and push** — So other agents know the task is blocked
4. **Ask for guidance** — Use the `ask_user_v2` tool to explain the issue

### 0.1.4.3 If the Task is Impossible

If a task cannot be completed as described (e.g., design flaw, missing dependency, technical limitation):

1. **Mark the task as `❌ FAILED`** — Set `Status` to `❌ FAILED`
2. **Document why** — Add the reason to `Notes`
3. **Commit and push**
4. **Move to the next task** — Do not block on failed tasks unless they are critical dependencies

## 0.1.5 Completing a Task

### 0.1.5.1 How to Mark Complete

When a task is fully implemented and verified:

1. **Run all unit tests** — Execute the full test suite for the affected module(s). Do NOT consider a task complete unless **all** unit tests pass.
2. **Fix other agents' code if needed** — If tests fail due to issues in another agent's code (e.g., a dependency task has bugs), fix those issues as part of completing your task. Do not leave broken tests for someone else.
3. **Set `Status`** to `✅ DONE`
4. **Set `End`** to the current date/time in ISO 8601 format: `YYYY-MM-DD HH:MM UTC`
5. **Update `Notes`** — Add a brief summary of what was implemented (1-2 sentences), including any fixes made to other agents' code
6. **Update `Files`** — Ensure all files created/modified are listed, including files modified in other agents' tasks

**Example — After completion:**

| ID | Task | Status | Assigned To | Owner | Start | End | Dependencies | Files | Notes |
|----|------|--------|-------------|-------|-------|-----|--------------|-------|-------|
| S0.1 | Create `emu_mod.c` with MODULE_DEPEND | ✅ DONE | Junie-Agent-1 | | 2026-04-26 04:37 UTC | 2026-04-26 05:15 UTC | | `sys/emulation/emu_mod.c` | Created module with MODULE_DEPEND on emu_core |

### 0.1.5.2 Commit and Push After Completion

After marking a task complete, commit and push:

```bash
git add -A
git commit -m "Complete task <ID>: <brief description>" --trailer "Co-authored-by: Junie <junie@jetbrains.com>"
git push
```

**Important:** You must push immediately after committing. Other agents working on the same branch need to see your completed work. The task completion is not effective until it is pushed to the remote repository.

Use `git add -A` to include all new/modified files from the implementation.

## 0.1.6 Handling Merge Conflicts

### 0.1.6.1 Before Pulling

Before pushing your changes, always pull the latest changes first:

```bash
git pull --rebase
```

If there are no conflicts, proceed with the push.

### 0.1.6.2 If a Merge Conflict Occurs

If `git pull --rebase` results in a merge conflict:

1. **Identify the conflicting file(s)** — Usually `.plan/<document>.md` files where task tables were modified
2. **Check if your task was taken** — Open the conflicting file and check the `Assigned To` column for your task ID:
   - **If another agent claimed your task**: Your task was taken. Abandon it and pick a different task.
   - **If no one claimed your task**: The conflict is likely from a different task. Resolve it.
3. **Resolve the conflict**:
   - Open the conflicting file
   - Look for `<<<<<<<`, `=======`, `>>>>>>>` markers
   - Keep both changes if they affect different tasks
   - If they affect the same task, keep the version that was committed first (the one already in the remote)
4. **Mark as resolved**:
   ```bash
   git add <conflicting-file>
   git rebase --continue
   ```
5. **Verify the file** — Open the resolved file and ensure all task tables are correct
6. **Push**:
   ```bash
   git push
   ```

### 0.1.6.3 Conflict Prevention Tips

- **Commit after each task** — Smaller commits reduce conflict surface area
- **Claim tasks quickly** — The first agent to claim and push owns the task
- **Work on different documents** — If possible, pick tasks from different documents to avoid file-level conflicts
- **Use the TOC** — Check [`0.0-Emulation-TOC.md`](./0.0-Emulation-TOC.md) to see which documents are being actively modified

## 0.1.7 Task Table Format

All task tables across all documents must use the following column format:

| ID | Task | Status | Assigned To | Owner | Start | End | Dependencies | Files | Notes |
|----|------|--------|-------------|-------|-------|-----|--------------|-------|-------|

**Column definitions:**

| Column | Description | Valid Values |
|--------|-------------|--------------|
| `ID` | Unique task identifier (e.g., `S0.1`, `AMD64.1`, `DEV.1`) | Alphanumeric with dots |
| `Task` | Brief description of the task | Free text |
| `Status` | Current status | `⬜ PENDING`, `🔄 IN PROGRESS`, `✅ DONE`, `🟡 BLOCKED`, `❌ FAILED` |
| `Assigned To` | Agent or person working on the task | Name or empty |
| `Owner` | Responsible party (if different from assignee) | Name or empty |
| `Start` | When work started (ISO 8601) | `YYYY-MM-DD HH:MM UTC` or empty |
| `End` | When work completed (ISO 8601) | `YYYY-MM-DD HH:MM UTC` or empty |
| `Dependencies` | Comma-separated list of task IDs that must be done first | Task IDs or empty |
| `Files` | Files created or modified by this task | File paths or empty |
| `Notes` | Implementation notes, blockers, or summary | Free text or empty |

---

## 0.1.8 Status Values

| Status | Meaning | Action Required |
|--------|---------|-----------------|
| `⬜ PENDING` | Not yet started | Available for claiming |
| `🔄 IN PROGRESS` | Being worked on | Do not claim |
| `✅ DONE` | Completed and verified | Ready for next phase |
| `🟡 BLOCKED` | Blocked by dependency or issue | Check Notes for reason |
| `❌ FAILED` | Cannot be completed as described | Check Notes for reason |

---

## 0.1.9 Agent Reminder

> **⚠️ Agent Reminder:** Before starting any task, always:
> 1. Pull the latest changes (`git pull --rebase`)
> 2. Check the task table for unclaimed tasks with met dependencies
> 3. Claim the task (update Status, Assigned To, Start)
> 4. Commit and push the claim
> 5. Implement the task
> 6. **Run all unit tests** — fix any failures, even in other agents' code
> 7. Mark complete (update Status, End, Notes)
> 8. Commit and push the completion
> 9. Move to the next task

## 0.1.10 Quick Reference — Git Commands

| Action | Command |
|--------|---------|
| Pull latest | `git pull --rebase` |
| Claim a task | `git add .plan/<doc>.md && git commit -m "Claim task <ID>" && git push` |
| Complete a task | `git add -A && git commit -m "Complete task <ID>: <desc>" && git push` |
| Resolve conflict | Edit file, `git add <file> && git rebase --continue` |
| Check status | `git status` |
| View log | `git log --oneline -10` |
